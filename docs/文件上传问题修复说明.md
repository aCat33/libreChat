# DeepSeek 文本附件上传问题修复（完整版）

## 问题描述

使用 DeepSeek 或其他端点时，出现以下问题：
1. ✅ 第一次上传文本或图片附件后解析成功
2. ❌ 再上传第二个不同类型的附件时：
   - 上传失败，或
   - 无法解析，或
   - **AI 回答的仍然是第一次附件的内容（即使第二次是完全不同的文件）**

## 根本原因分析

问题有**两个层面**：

### 1. 文件流未关闭（底层问题）

在文件解析过程中，Node.js 的 `createReadStream` 创建的文件流没有被正确关闭，导致：
- 文件句柄泄漏
- 内存缓存污染
- FormData 对象缓存了之前的文件引用

### 2. **消息上下文缓存（关键问题）** ⭐

更严重的问题是 **`fileContext` 持久化在消息对象中**：

1. **第一次上传**：
   - PNG 图片上传
   - `addFileContextToMessage()` 提取图片信息
   - 将 `fileContext` 添加到 `latestMessage` 对象
   - 消息保存到数据库，`fileContext` 也被保存

2. **第二次上传**（同一对话中）：
   - 上传文本文件
   - 从数据库加载消息历史，**旧消息仍然带有第一次的 `fileContext`**
   - 虽然新的 `fileContext` 被添加，但**旧的没有被清除**
   - AI 看到了两次的文件上下文，但优先处理了第一次的

**关键代码位置**：
- [BaseClient.js#addFileContextToMessage](c:\Users\10211\Desktop\AI Files\LibreChat\api\app\clients\BaseClient.js#L1281): 没有清除旧的 `fileContext`
- [AgentClient.js#buildMessages](c:\Users\10211\Desktop\AI Files\LibreChat\api\server\controllers\agents\client.js#L398): 直接在旧消息上叠加新的 `fileContext`

## 解决方案

### 修复 1: 文件流管理（底层修复）

**修改文件**: `packages/api/src/files/text.ts`

```typescript
// ✅ 修复后的代码
let fileStream: NodeJS.ReadableStream | null = null;
try {
  const jwtToken = generateShortLivedToken(userId);
  const formData = new FormData();
  formData.append('file_id', file_id);
  
  // 保持流的引用以便清理
  fileStream = createReadStream(file.path);
  formData.append('file', fileStream);

  // ... 上传逻辑 ...

} catch (error) {
  // ... 错误处理 ...
} finally {
  // ⭐ 关键：确保文件流被正确关闭
  if (fileStream && typeof (fileStream as any).destroy === 'function') {
    (fileStream as any).destroy();
  }
}
```

### 修复 3: 清除旧的 fileContext（关键修复）⭐

**修改文件**: `api/app/clients/BaseClient.js`

```javascript
async addFileContextToMessage(message, attachments) {
  // 🔧 清除旧的 fileContext 防止缓存污染
  if (message.fileContext) {
    delete message.fileContext;
  }

  const fileContext = await extractFileContext({
    attachments,
    req: this.options?.req,
    tokenCountFn: (text) => countTokens(text),
  });

  if (fileContext) {
    message.fileContext = fileContext;
  }
}
```

### 修复 4: Agent 客户端处理

**修改文件**: `api/server/controllers/agents/client.js`

```javascript
if (this.options.attachments) {
  const attachments = await this.options.attachments;
  const latestMessage = orderedMessages[orderedMessages.length - 1];

  // 🔧 清除旧的 fileContext 防止混淆
  if (latestMessage.fileContext) {
    delete latestMessage.fileContext;
  }

  if (this.message_file_map) {
    this.message_file_map[latestMessage.messageId] = attachments;
  } else {
    this.message_file_map = {
      [latestMessage.messageId]: attachments,
    };
  }

  await this.addFileContextToMessage(latestMessage, attachments);
  const files = await this.processAttachments(latestMessage, attachments);

  this.options.attachments = files;
}
```

## 为什么需要这些修复？

### 修复 1 & 2 - 文件流清理
- **无论成功或失败都执行**：确保流总是被关闭
- **防止资源泄漏**：即使发生异常也能清理资源
- **Node.js 最佳实践**：所有 ReadStream 都应该显式关闭

### 修复 3 & 4 - fileContext 清理 ⭐
- **防止上下文污染**：每次上传都重新提取文件上下文
- **确保数据一致性**：新附件对应新的上下文
- **解决混淆问题**：避免 AI 看到多个文件的混合上下文

**场景说明**：

**修复前**：
```javascript
// 第一次上传 PNG
message.fileContext = "图片文件：Snipaste_2026-01-28.png\n内容：截图..."

// 第二次上传 TXT（同一对话）
message.fileContext = "图片文件：Snipaste_2026-01-28.png\n内容：截图..." // ❌ 旧的还在！
                    + "文本文件：新建文本文档.txt\n内容：..."

// AI 看到两个文件的上下文，优先处理了旧的
```

**修复后**：
```javascript
// 第一次上传 PNG
message.fileContext = "图片文件：Snipaste_2026-01-28.png\n内容：截图..."

// 第二次上传 TXT（同一对话）
delete message.fileContext; // 🔧 清除旧的
message.fileContext = "文本文件：新建文本文档.txt\n内容：..." // ✅ 只有新的

// AI 只看到当前文件的上下文
```

1. **RAG API 配置**：如果启用了 RAG_API_URL，文本解析会优先使用 RAG API
2. **超时设置**：RAG API 请求超时为 300 秒（5 分钟）
3. **回退机制**：如果 RAG API 失败，会自动回退到本地解析
4. **内存使用**：修复后不会因为文件流泄漏而累积内存使用
